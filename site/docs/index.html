checkmeter · inspection manual

Checking the meter on an AI coding plan

checkmeter reads the session files Codex and Claude Code already write, puts the vendor's usage meter next to the tokens those same files logged, and reports the readings that don't add up. It reads files and prints a report. It never sends anything anywhere.

§1 Install

You need Node.js 18.18 or newer. There are no runtime dependencies.

# run straight from GitHub (builds once, then cached by npm)
npx github:Blackman99/checkmeter

# or install the release tarball globally
npm install -g https://github.com/Blackman99/checkmeter/releases/download/v0.1.0/checkmeter-0.1.0.tgz
checkmeter --version

Not sure it'll find anything? checkmeter --demo builds a generated week of Codex and Claude Code files in a temp folder and runs the full report on it, so you can see every kind of finding before pointing it at your own files. Demo output is labelled DEMO DATA everywhere.

§2 Usage

With no arguments, checkmeter looks at the last 7 days:

checkmeter                       # same as: checkmeter report --days 7
checkmeter --days 14 --harness codex
checkmeter --since 2026-10-14
checkmeter --json | jq '.findings[] | {kind, title}'

The report has two parts. Readings that don't add up comes first: one block per finding, with the numbers and the file:line of the readings it is based on. Then Where the meter went: for each harness, the sessions that moved the 5-hour and weekly meters most, in meter points, with a short "why" (near context limit, fast tier, cache rebuilt after idle, subagent…). A last line says how many points no local session accounts for.

§3 Findings

Every finding compares the meter with itself. checkmeter never assumes a published limit, because the vendors don't publish one in tokens. Severity: ✖ flag is worth asking about, ◆ review is worth a look, · note is context.

FAST METER
On one or more days the meter moved at least --fast-ratio (default 2) times your baseline rate, by at least 3 points. The finding prints the model mix and the share of priority/fast-tier requests on those days next to your baseline days, so "I switched to a bigger model" is easy to rule in or out.
OFF-LEDGER
Between two readings in the same window the meter rose by points that the requests logged on this machine can't account for, even at that day's own rate. Fires at 3 points or more, at least 2.5 above what your usage explains. Typical causes: Codex cloud tasks, another computer on the same account, the desktop app, a workspace sharing the pool. Sometimes nothing you did.
STUCK RESET
A reading taken after the window's resets_at still shows the old percentage and the old reset time (10 minutes of grace for the 5-hour window, an hour for the week).
PLAN CHANGED
The plan_type inside the readings switched. A switch that comes back (pro → plus → pro) is one flagged finding with the length of the stretch, and if a FAST METER finding covers the same days the two are linked. A one-way switch is a ◆ review: if you didn't change plans, the meter is applying another plan's limits from there on.
METER DROP
The meter went down without a reset: a correction or a credit on the vendor side.
CACHE TTL
Claude Code only. A client version that wrote the 1-hour prompt cache was followed by versions that wrote only the 5-minute cache. A 5-minute cache goes cold during any pause over 5 minutes and the next request pays to write the whole context again.
LIMIT HIT
The client logged that a rate limit was reached, with the meter value at the time.
NO BASELINE
Fewer than 3 days with enough work to say what "normal" is. FAST METER and OFF-LEDGER need a baseline, so they stay quiet until there is one.

§4 Recording the Claude Code meter

Codex writes its meter into every rollout file, so there is nothing to set up. Claude Code shows the meter to its status line (rate_limits.five_hour and seven_day) but doesn't keep it in the transcripts. checkmeter record is a status-line command that saves those readings to ~/.checkmeter/claude-meter.jsonl and prints a short line of its own.

checkmeter setup claude           # show the change to ~/.claude/settings.json
checkmeter setup claude --write   # apply it; the old file is kept as settings.json.checkmeter-backup-…

If you already have a status line, setup keeps it: the new command is checkmeter record --then '<your old command>', which runs your command with the same input and prints its output followed by │ ⛽ 5h 24% · wk 41% · cache 5m (plus · out 11:37 when the pace empties the 5-hour window before it resets). A reading is only appended when it changed or 10 minutes passed, so the log stays small. Readings exist from the day you run setup; older Claude Code sessions show "before the meter was recorded".

§5 Pace and the guard

Pace forecast

The report's PACE section reads each open window forward: at the rate you're going now, when does it reach 100%, and is that before it resets? It is in --json as pace and in the analyser on the home page too.

PACE  where each open window is heading at the rate you're going now
  claude 5h    50.3% now · 32 pts/h since 09:03 · runs out ≈ 11:37, 1 h 40 min before the reset at 13:17
  claude week  36.6% now · 7.0 pts/day since Sat 24 Oct · on pace for 44% at the reset (Thu 29 Oct 10:00)
  codex  5h    6% now · idle since 01:36; the window resets at 06:21
  • 5-hour window. The rise over the last hour of readings in the current window (or since the window opened, if that's sooner), idle minutes included. With no reading for 30 minutes the window is idle and gets no forecast; under 10 minutes of readings is too early to call.
  • Week. Points per calendar day since the first reading in the window, because a one-hour rate would assume you code around the clock. It needs 6 hours of readings.
  • Status line. checkmeter record adds out 11:37 only when the 5-hour window runs out before it resets. Otherwise the line stays as it was.
  • A window whose reset time has passed is left out: it already rolled over, and the new one has no pace yet. A credit inside the window (METER DROP) doesn't restart it.

The guard

checkmeter guard is meant to run as a PreToolUse hook. It reads the newest meter reading (the newest Codex rollout, or the Claude Code meter log) and exits 2 with a message on stderr when a meter is at or over the line. Both clients treat exit 2 as "block this tool call and show the reason to the model", so the agent stops and reports instead of getting cut off halfway through an edit.

checkmeter setup guard codex      # prints the [[hooks.PreToolUse]] block for ~/.codex/config.toml
checkmeter setup guard claude     # prints the hooks.PreToolUse block for ~/.claude/settings.json
checkmeter setup guard codex --max-5h 80 --max-week 90

Readings older than 6 hours, or from a window that has already reset, never block. The guard exits 0 when it finds no reading at all.

§6 Evidence pack

checkmeter evidence -o meter-evidence.md writes the flagged findings as a markdown document you can attach to a support ticket: the period in UTC, a summary table, then for each finding its details, every reading it rests on (UTC time, local time, value, reset time, plan, file:line) and one sed -n 'Np' file | jq line per reading so the person reading it can check each number in the raw file. It contains no prompts, responses or code. It's written in the first person because you're the one sending it.

§7 Configuration

There is no config file. Paths follow the clients' own conventions:

whatdefaultoverride
Codex sessions~/.codex/sessions, ~/.codex/archived_sessions$CODEX_HOME, --codex-home
Claude Code transcripts~/.claude/projects/**.jsonl (subagents included)$CLAUDE_CONFIG_DIR, --claude-dir
Claude Code meter log~/.checkmeter/claude-meter.jsonl$CHECKMETER_HOME, --meter-log
home folder for all of the aboveyour home--home
colouron for a terminalNO_COLOR, FORCE_COLOR; --color / --no-color win over both

Compressed rollouts (.jsonl.zst) are read when a zstd binary is on the PATH and skipped with a note otherwise.

§9 How it computes

  • Readings. Codex: rate_limits.primary (300-minute window) and secondary (10080-minute window) of each token_count event, with used_percent, resets_at, plan_type. Claude Code: the recorded status-line snapshots.
  • Weighted tokens. Requests count at API price ratios so cached input doesn't look as expensive as new input. Codex: uncached input 1, cached input 0.1, output 8. Claude: input 1, cache read 0.1, 5-minute cache write 1.25, 1-hour cache write 2, output 5.
  • Duplicates. Codex subagent rollouts replay their parent's history; Claude Code writes a streamed message several times. Each request is counted once, keyed by its own identity, not by file.
  • Intervals. Consecutive readings of one window form an interval; a reset (new resets_at, value drops) starts a new one. Each interval's points are shared among the sessions active in it, in proportion to their weighted tokens.
  • Pace. 5-hour: (used now − used an hour ago) per hour, projected from the newest reading to 100% or to resets_at. Week: (used now − used at the window's first reading) per day, projected the same way. Readings belong to one window while resets_at stays within 10 minutes (an hour for the week).
  • Baseline. The median over days with at least 0.2M weighted tokens and 1 point of movement, of points per million weighted tokens. At least 3 such days are needed.

§10 FAQ

Does it upload anything?
No. There is no network code in checkmeter. The browser analyser on the home page runs in the tab; nothing leaves it.
Is a finding proof that I was overcharged?
No. It's a reading that doesn't match your own history on this machine. Usage from other machines and cloud tasks is invisible here and shows up as OFF-LEDGER. The evidence pack is written so someone can check it, not as an accusation.
Why are my Claude Code sessions showing "—"?
The Claude Code meter is only recorded from the day you run checkmeter setup claude. Token totals are still shown for older sessions.
How precise is it?
Codex logs whole percents, so one reading is ±0.5 points. The thresholds (3 points, 2× baseline) are set well above that.
How is this different from ccusage or a token counter?
Token counters add up what you spent. checkmeter is about the other side: the vendor's meter. It checks the meter readings against your spending and says which ones don't fit.
Does it work with OpenCode, Gemini CLI, Cursor…?
Not yet. They don't log a vendor meter in a way checkmeter can read today. See the roadmap.
It got something wrong.
Please open an issue with the finding and, if you can, the two lines it points to (meter readings only, no prompts).
