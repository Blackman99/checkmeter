Your AI coding plan has a meter: a 5-hour bar and a weekly bar. The meter readings, and every token you spent, are already in files on your disk. checkmeter puts the two side by side and tells you which readings don't add up.

PUMP 01

The readings are already on your disk

Codex writes the vendor's meter into every token_count event of its rollout files: used_percent for the 5-hour and weekly windows, when each resets, and the plan it thinks you're on. Check yours right now:

grep -rho '"used_percent":[0-9.]*' ~/.codex/sessions | tail

Claude Code hands the same two meters to its status line on every reply. checkmeter setup claude wraps your status line (keeping it as it is) so those readings get logged too. From then on both sides of the ledger are local, plain JSON, and yours.

PUMP 02

What the inspection can say

Every finding compares the meter with itself: your usual points per million weighted tokens on steady days. No published limit is assumed.

  • FAST METERA day where the meter moved 2× or more faster than your baseline for the same model and speed tier, with the model mix printed so you can rule out the obvious.
  • OFF-LEDGERThe meter rose by points that no session on this machine logged. Cloud tasks, another laptop, a shared workspace pool, or something you'd want to ask about.
  • STUCK RESETThe reset time passed and the window didn't roll over: readings after it still show the old percentage and the old reset time.
  • PLAN CHANGEDThe plan_type inside the readings switched, or switched and came back: "plus" limits for 30 hours between "pro" readings is what a stretch metered against the wrong plan looks like on disk.
  • METER DROPThe meter went down without a reset: a correction or a credit. Worth matching against any email you got.
  • CACHE TTLClaude Code stopped writing the 1-hour prompt cache after an update, so every pause over 5 minutes pays to rebuild the context.
  • ADDS UPThe meter moved the way your own usage says it should. Most windows look like this, and the report says so plainly.

PUMP 04

Hand the inspector's report to support

checkmeter evidence -o meter-evidence.md writes the flagged readings up as a ticket: a summary table, each reading with its UTC time and file:line, and a one-line sed | jq for each so whoever reads it can check the numbers against the raw files. No prompts, no code, no responses.

PUMP 05

A guard before the meter runs dry

Hitting the 5-hour wall halfway through a refactor is the expensive way to find out. checkmeter guard reads the newest reading and exits 2 with a plain message once you cross your line (90% of the 5-hour window, 95% of the week by default), so the agent stops cleanly instead of mid-edit.

# print the hook block for your client, paste it where it says
checkmeter setup guard claude     # → ~/.claude/settings.json  hooks.PreToolUse
checkmeter setup guard codex      # → ~/.codex/config.toml     [[hooks.PreToolUse]]

# what the agent sees when it trips
checkmeter guard: the Codex 5-hour meter is at 93% (guard line 90%). It resets
Wed 21 Oct 14:12 (in 38 min). Stop here and tell the user how far the task got,
or ask them to raise --max-5h.
PUMP 06

What an inspector can't see

  • Only what this machine logged. Usage from another computer or the cloud shows up as OFF-LEDGER, which is the point, but checkmeter can't say which of those it was.
  • Codex logs readings as whole percents, so a single reading is ±0.5 pts. Findings need several points of difference before they fire.
  • Claude Code doesn't keep meter readings in its transcripts; they exist from the day you run setup claude. Before that, sessions show "before the meter was recorded".
  • A finding is a reading that doesn't match your own history, not proof of a billing error. The evidence pack is written to be checked, not to accuse.
